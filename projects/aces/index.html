Integrating AI agents via LLM APIs as financial analysts that focus on technical analysis of the market.

Why I built this

I've traded enough on my own to achieve some level of profit, now that I have traded for over a few years. I still don't know a lot about trading but at least I can testify with my revenue rate, which is above X% from my baseline at the moment. However, this was to experiment and get myself used to trading so the amount of seed used was very small. Recently, AI and especially LLMs have been changing the world in almost every domain. I got curious about automated trading with AI agents and started looking into Agentic AI systems. I wanted to test whether a multi-agent system built to read the market can arrive at a decision to automate trading so one could earn profits without governing and hovering over the system to make decisions. And if so, how can one achieve the best possible profit and maximize their revenue?

Which factors can affect the performance greatly

We can all agree that from the Pareto principle that 20% of the core changes can lead to 80% of the performance. In agentic AI systems what could be those 20%? I thought these following factors were based on researching and learning about agentic AI systems:

  1. What model is one using?
  2. What framework is one using?

Although, Rasheed et al.'s 2026 study on comparing agentic frameworks for reasoning tasks (three benchmarks: BBH, GSM8K, ARC) revealed that framework choice should be driven by memory management, failure handling and cost control, not accuracy - as most frameworks achieved very similar overall performance. This is why I chose to use LangChain, for a budget friendliness and implementing reflexion as a loop.

Structure of A.C.E.S

Every decision — LONG or SHORT (USDJPY), hourly — passes through the same four-stage read regardless of which architecture is running it:

  • Indicator — Relative Strength Index (momentum indicator), MACD (Mean Average Convergence Divergence), Stochastic Oscillator, Rate of Change (ROC, momentum oscillator), Williams %R (momentum indicator), Average True Range (ATR, for dynamic stop-loss), Bollinger Bands (Momentum and Volatility) are actually computed not estimated by the model, and handed over as numbers.
  • Pattern — a rendered candlestick chart, read by a vision-capable model for classical reversal/continuation formations — the model looks at the actual image, not a text description of it.
  • Trend — the same chart, now annotated with fitted support/resistance lines, read for structure and with/counter-trend positioning.
  • Decision — weighs all three reads into a directional call, a risk-reward ratio, and an ATR-scaled stop — the number that actually gets risked.

What changes between architectures is how those four stages talk to each other — a parallel LangGraph pipeline, an AutoGen debate where the specialists cross-examine each other, a DSPy program whose prompts are optimized against realized P&L instead of hand-tuned, and a LangGraph variant where a fifth agent reflects on the decision before it ships.

From linear to parallel

First thing that caught my attention was the fact that initial design was linear. This project builds on QuantAgent (the GitHub repo has since been renamed QuantHarness), a price-driven multi-agent trading system - there are four agents which analyzes Indicators, Patterns, and Trends as a strict relay, each one waiting on the last before the Decision Agent makes the final decision

Indicator, Pattern, and Trend don't depend on each other's output — only the Decision Maker needs all three. Also, I checked the original paper's repo and actually found out that their agents are not dependent on each other's output except for the decision making agent thus parallel structure shouldn't hurt. One could argue that CoT(Chain of Thought)-like structure could provide better outcomes but in reality I think the conformity can actually harm the agents. So I'm going to stick to the parallel structure unless the test results say otherwise. The parallel design cuts end-to-end latency by roughly 28%, with no change to what any individual agent sees or does. Same four specialists, same prompts — just no longer waiting in line.

It's also worth noting that the original QuantAgent paper never explains the sequential choice.

Validating the best model+framework for A.C.E.S

The trap here is obvious in hindsight: if you swap both the model and the architecture at once and the numbers change, you've learned nothing about which one caused it. So the whole study is sequenced to isolate exactly one variable per phase:

  1. Phase 0 — Baseline & repeatability (done). Two checks over the same week: five identical runs of the current parallel model mix, to see how much a single model's own results move around on nothing but ordinary LLM nondeterminism before that noise gets mistaken for a real signal later — and a head-to-head between that parallel baseline and the original QuantAgent series pipeline running its original prompt, so the series-vs-parallel question gets measured, not assumed, before any phase that follows builds on it.
  2. Phase 1 — Model, architecture held constant (in progress). DeepSeek + Gemini vs. all-MiniMax-M3, both on the same LangGraph pipeline, same window, five replicates each.
  3. Phase 2 — Architecture, model held constant (pending). Whichever model wins Phase 1, tested across all four architectures. Each one now runs its own full pipeline independently — nobody reuses another system's analysis, so cost and latency are honestly comparable, not just decision quality.

Criteria for choosing

I.Price & token economics

Every decision is four real model calls, and two of them look at an image — vision tokens aren't free. Here's where the three models actually sit, per million tokens:

ModelInputOutputRole in the study
DeepSeek V4 Pro$0.435$0.87baseline-mix — text stages
Gemini 3 Flash$0.50$3.00baseline-mix — vision stages
MiniMax-M3$0.30$1.20candidate — all four stages

The output-price gap is the interesting part: Gemini's $3.00/M output is currently carrying both vision stages in the baseline mix. Worth being precise about what that figure actually is — Gemini 3 Flash Preview's own pricing lists one input rate covering text, image, and video alike ($0.50/M) and a single output rate ($3.00/M), because this model only ever writes text back; it doesn't generate images, so there's no separate "image price" being paid here. The rate itself doesn't care whether the input was a chart or a sentence — what actually drives cost is how many tokens the chart tokenizes into, not a higher per-token charge for looking at it. If MiniMax-M3 can read the same charts competently, the two most expensive calls in the whole pipeline get a lot cheaper — that's a real, quantifiable incentive to switch, if it holds up under criterion two. MiniMax's rate is also a standing 50% promotional cut off its own list price, which is its own note to self: don't build a permanent cost model on a promotional number.

That list pricing shows up in independent measurement too. Artificial Analysis's per-task cost figures (actual observed spend, not sticker price) put DeepSeek V4 Pro as the cheapest model in its intelligence-benchmark comparison set at $0.04/task, with MiniMax-M3 at $0.12/task — both well below the frontier models they're being weighed against. The gap holds on coding-agent tasks too, where DeepSeek V4 Pro came in at $0.27/task against $2–12+ for the frontier options in that comparison.

Pricing as researched during this write-up — see MiniMax M3, DeepSeek V4 Pro, and Gemini API pricing for list rates; Artificial Analysis's model comparison and coding-agent benchmarks for measured cost-per-task.

II.Capability (Intelligence)

I started with Artificial Analysis's Intelligence Index — a composite across nine evals including GPQA Diamond, Humanity's Last Exam, and MMMU-Pro for visual reasoning, so multimodal capability is already part of what it's measuring, not something I had to check separately. On that index, DeepSeek V4 Pro and MiniMax-M3 land tied at value of 44. They are both within top 15. However, the tie is exactly why this can't be settled by leaderboard alone.

I thought this would be a good place to have a benchmark closer to the finance domain. Vals AI's Finance Agent v2 — entry-level financial-analyst tasks against real filings — has MiniMax-M3 at 48.27% (rank 17 of 40 models tested) against DeepSeek V4 at 44.08% (rank 24 of 40), with MiniMax-M3 also costing about a third as much per test and running roughly 3x faster on that benchmark. Tied on general intelligence, ahead on the closest available proxy for this task, and cheaper doing it. That's another reason to take MiniMax-M3.

Sources: Artificial Analysis Intelligence Index; Vals AI Finance Agent v2.

III.Hallucination & inconsistency

This is the one that actually bit me already, in a different form. Early on, the vision agents would occasionally state a support level miles outside what the chart could possibly show — confidently citing a price the y-axis never contained. The fix was to explicitly anchor the prompt to the chart's real close and range before asking for an opinion, which stopped it. That's the category of failure this criterion watches for: not "wrong direction," but the model stating something false about the input it was just shown.

The other half is a subtler kind of inconsistency the backtest surfaced independently: this system's worst losses tend to come from all three specialists agreeing confidently right at a reversal — a unanimous, high-conviction, wrong call. Two of the four architectures (the AutoGen debate and the Reflexion variant) exist specifically because of that finding.

And here's the concrete reason I insisted on re-testing MiniMax fresh instead of carrying over an old impression: on that same Finance Agent v2 benchmark, MiniMax-M3 scores 48.27%.

Source: Vals AI Finance Agent v2 — MiniMax-M3 vs. MiniMax-M2.7.

Choosing my frameworks

Agent frameworks split roughly into four families. Before narrowing to what's actually in Phase 2, it's worth showing the full board and being honest about which of these I'm planning to test.

Phase 1 is specifically designed so I don't need one until the model question is settled first. I suspect DSPy will perform the best with its innate ability to CoT and reflect/feedback. Here are frameworks I think are worth testing for Phase 2:

  • LangGraph — the original baseline framework. This is chosen for its token efficiency and expandability of complex decision making such as integrating reflexion for improving judgements.
  • AutoGen — the same three specialists as a moderated debate, each forced to state the strongest reason its own read could be wrong before a closing synthesizer outputs the final decision.
  • DSPy — structurally identical to the LangGraph baseline, but the prompts aren't hand-written — an optimizer searches for the instructions and few-shot examples that maximize profit.
  • LangGraph + Reflexion — the baseline plus one addition: a reflector critiques the decision against the same reversal failure mode and can send it back for a bounded number of revisions before it ships.

Note: I'm highly skeptical of AutoGen's efficiency and performance here, especially with several studies noting debating doesn't necessarily lead to better performance and can lead to high cost.
